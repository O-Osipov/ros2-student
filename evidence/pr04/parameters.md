# ПР04: параметры работающей ноды patrol

Дата опыта: 19 октября 2026 года. Ветка `pr04` создана локально от личной
`pr03`, потому что ветка преподавателя `origin/pr04` отсутствовала. Работа
выполнена в существующем контейнере с ROS 2 Lyrical и настоящим turtlesim
при `QT_QPA_PLATFORM=offscreen`, `ROS_DOMAIN_ID=48` и
`ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`. Окно не показывалось; проверены
ROS-сообщения, параметры и состояние процесса. Полный вывод — в
[tests.txt](tests.txt), исходный сбой — в [defect.txt](defect.txt).

## Проверка и применение параметров

`linear_speed` по умолчанию равен 0.5 м/с и допускает [0, 1].
`turn_rate` равен 0.3 рад/с и допускает [−1, 1]. `publish_hz` равен
10.0 Гц и допускает [1, 30]. Все три значения должны быть конечными числами.
Чистая функция `validate_settings` проверяет полный кандидат настроек;
обработчик `on_set` отклоняет неподходящий набор до изменения активного
состояния. После принятия `post_set` отменяет и уничтожает старый таймер,
создаёт один новый с периодом `1/publish_hz` и применяет скорости.
Начальные значения также проверяются до создания первого таймера.

До первой `Pose` публикуется нулевой `Twist`. После первой позы в команду
попадают принятые `linear_speed` и `turn_rate`. Подписка на позу и remap
`cmd_vel:=/turtle1/cmd_vel` сохранены из ПР03.

## Исправная работа и смена частоты

Открытые команды для повторения после `source /opt/ros/lyrical/setup.bash`
и `source install/setup.bash`:

```bash
ros2 launch turtle_bringup sim.launch.py
ros2 run patrol patrol --ros-args -r cmd_vel:=/turtle1/cmd_vel
ros2 param get /patrol publish_hz
ros2 param set /patrol linear_speed 0.7
ros2 param set /patrol turn_rate -0.2
ros2 param set /patrol publish_hz 5.0
ros2 topic hz /turtle1/cmd_vel
```

В автоматизированном живом опыте до изменений получено 22 сообщения за
~2,2 с: **9,998 Гц**, `Twist=(0.5, 0.3)`. Три команды `ros2 param set`
ответили `Set parameter successful`. После изменения наблюдатель получил
16 сообщений за ~3,2 с: **4,999 Гц**, `Twist=(0.7, -0.2)`.
Тест ноды также подтвердил, что после пересоздания остался ровно один таймер
с периодом 200 мс.

## Сломать: ноль без проверки

Для дефектного опыта временно удалена регистрация
`add_on_set_parameters_callback`; после опыта строка восстановлена без
коммита. В отдельном домене 49 работал `ros2 run patrol patrol`.
Команда `ros2 param set /patrol publish_hz 0.0` привела к завершению ноды
с кодом **1** и `ZeroDivisionError: division by zero` в
`self.create_timer(1.0 / new_hz, self.tick)`. Клиент `ros2 param set`
не получил ответ и истёк его 10-секундный таймаут. Это реальный отказ
работающего ROS-процесса, а не искусственное исключение в тесте.

## Доказать: ноль отклонён, поток сохранён

После восстановления проверки тот же `ros2 param set /patrol publish_hz
0.0` вывел в stderr `Setting parameter failed: publish_hz must be a finite
number in [1.0, 30.0]`. `ros2 param get` показал прежние **5.0**, а поток
сохранился на **5,000 Гц**. Аналогично `-1.0` отклонён, поток остался около
5 Гц. ROS CLI в этой версии возвращает код процесса 0 даже при отказе
параметра; вывод ошибки, значение параметра и частота проверены вместе.

Чистые тесты отдельно проверили допустимый переход 10→5 Гц, ноль,
отрицательное значение, NaN, бесконечность и границы скоростей. При
атомарной попытке изменить одновременно частоту на 0 и скорость на 0.9
ни одно активное значение и объект таймера не изменились. Начальный
`publish_hz=0.0` теперь даёт `ValueError` до создания таймера.

## Готовые сервис и действие

```bash
ros2 service call /clear std_srvs/srv/Empty '{}'
ros2 action list -t
```

`/clear` ответил `std_srvs.srv.Empty_Response()`; действие обнаружено как
`/turtle1/rotate_absolute [turtlesim_msgs/action/RotateAbsolute]`.
Сервис `/clear` обрабатывает короткий запрос и возвращает один ответ после
очистки следа. Действие поворота принимает цель, во время исполнения может
передавать обратную связь, а затем возвращает результат; цель можно отменить.
